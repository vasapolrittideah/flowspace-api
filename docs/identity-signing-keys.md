# Rotate local Identity signing keys

Identity signs access tokens with the private key in `.secrets/identity-signing-key.pem`. Tilt mounts that file only in the Identity API. Identity publishes its public key at `/.well-known/jwks.json` on the internal Service. `SIGNING_KEY_ID` names the active key. `SIGNING_ADDITIONAL_PUBLIC_KEY` publishes one more Ed25519 public key as `<kid>:<base64url-public-key>`; it never contains a private key.

Use this sequence for routine rotation in the disposable local cluster. Keep Tilt running, work on a short-lived branch, and use a new key ID for every rotation. Do not commit files under `.secrets/`.

After each local ConfigMap or Secret change, wait for Tilt to apply it, then run `kubectl --context k3d-flowspace -n flowspace-local rollout restart deployment/identity-api` and `kubectl --context k3d-flowspace -n flowspace-local rollout status deployment/identity-api`. In another terminal, run `kubectl --context k3d-flowspace -n flowspace-local port-forward service/identity-internal 18081:8081`. Read JWKS with `curl -fsS http://127.0.0.1:18081/.well-known/jwks.json`.

1. Generate a replacement private key outside Git. Run `test ! -e .secrets/identity-signing-key-next.pem && (umask 077; openssl genpkey -algorithm ED25519 -out .secrets/identity-signing-key-next.pem)`. Derive its public value with `node -e 'const {createPrivateKey,createPublicKey}=require("node:crypto");const {readFileSync}=require("node:fs");console.log(createPublicKey(createPrivateKey(readFileSync(".secrets/identity-signing-key-next.pem"))).export({format:"jwk"}).x)'`.
2. Set `SIGNING_ADDITIONAL_PUBLIC_KEY` in `deploy/overlays/local/identity/kustomization.yaml` to the new ID and public value. Let Tilt apply the ConfigMap, then restart `identity-api`. Check that the internal JWKS publishes both IDs. Wait at least 60 seconds after both IDs appear so a verifier can refresh its JWKS cache before Identity uses the new private key.
3. Derive and save the current key's public value with the same Node command, using `.secrets/identity-signing-key.pem`. Run `test ! -e .secrets/identity-signing-key-old.pem && cp .secrets/identity-signing-key.pem .secrets/identity-signing-key-old.pem`, then run `mv .secrets/identity-signing-key-next.pem .secrets/identity-signing-key.pem`. Change `SIGNING_KEY_ID` to the new ID and set `SIGNING_ADDITIONAL_PUBLIC_KEY` to the old ID and saved public value. Let Tilt apply the Secret and ConfigMap, restart `identity-api`, and check that both IDs remain in JWKS. After the rollout completes, run `old_id=$(awk -F'[:=]' '/SIGNING_ADDITIONAL_PUBLIC_KEY=/ {print $2}' deploy/overlays/local/identity/kustomization.yaml); printf '%s:%s\n' "$old_id" "$(date -u +%s)" > .secrets/identity-signing-old-key-last-use` to record the old key ID and its last possible use.
4. After at least 690 seconds have elapsed since the recorded time, run `task identity:signing-key:retire`. The task refuses to remove the old public key before the delay ends. Let Tilt apply the ConfigMap, restart `identity-api`, and check that JWKS contains only the new ID. The delay covers the ten-minute access-token lifetime, 30-second clock margin, and 60-second JWKS cache bound.

Keep the prior private file outside Git until the rotation is reviewed. If the prior key may be compromised, follow the emergency procedure in [ADR-0035](adr/0035-identity-signup-security-and-mail-delivery.md): stop signing with it, remove its public key, revoke affected sessions, and require login after the replacement is published. Do not use the routine overlap for a compromised key.
