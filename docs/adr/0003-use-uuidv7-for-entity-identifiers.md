# ADR-0003: Use UUIDv7 for all entity identifiers

- **Status:** Accepted
- **Date:** 2026-09-05
- **Deciders:** Vasapol Rittideah
- **Tags:** `data`

## Context

Every aggregate in FlowSpace needs an identifier, and the choice is load-bearing
in three places at once: it is half of every primary key, it is repeated in
every index and foreign key, and it is public — identifiers appear in URLs, in
logs, in saved API collections, and in support conversations. Changing it later
means rewriting every migration, every query, and every client that stored a
link.

Two constraints from decisions already taken shape the answer.

The primary key is composite, `(workspace_id, id)` (ADR-0002), so the
identifier is not alone in the index; whatever it costs in bytes is paid on top
of 16 bytes of `workspace_id` in every index entry and every foreign key.

Rows are created in one service and referenced in another, and an outbox row is
written in the same transaction as the aggregate it describes. The identifier
must therefore exist *before* the transaction commits, which rules out asking
the database to assign it.

Finally, the database node has 32 GB of RAM shared with every other workload on
the box. Index locality is not a micro-optimisation here: a randomly ordered
index key turns each insert into a page split somewhere unpredictable, writes a
full page to the WAL, and evicts unrelated pages from a buffer cache that is
already small relative to the data.

## Decision

All entity identifiers are **UUIDv7** (RFC 9562), generated by the application,
stored in a native PostgreSQL `uuid` column.

- Generation happens in Go via `github.com/google/uuid`, which supplies a
  monotonic counter within a single millisecond. PostgreSQL's own `uuidv7()`
  is not used, because the identifier is needed before the statement runs.
- Storage is `uuid` (16 bytes). Never `text`, never `varchar(36)`.
- Ordering by identifier is ordering by creation time to **millisecond
  precision and no better**. It is a locality property, not a guarantee.
  Anything that needs real ordering — an activity feed, an event log, a
  cursor — carries its own timestamp or sequence column and does not sort by
  identifier.

The public representation is the canonical hyphenated UUID with a
per-aggregate prefix:

| Aggregate | Prefix | Public form                               |
| --------- | ------ | ----------------------------------------- |
| Workspace | `ws_`  | `ws_018f4e6a-9c1b-7c3d-8e2f-1a2b3c4d5e6f` |
| Project   | `pj_`  | `pj_018f4e6b-1d02-7a44-b91c-0f5e8d7a6b21` |
| Work item | `wi_`  | `wi_018f4e6b-1d02-7a44-b91c-0f5e8d7a6b22` |
| User      | `us_`  | `us_018f4e5f-77aa-7b10-9c3d-2e4f6a8b0c1d` |

The prefix is part of the API contract. Parsing rejects an unknown prefix, and
rejects a correctly formed identifier carrying the wrong prefix for the
position it appears in, which turns "project id passed where a work item id was
expected" from a 404 into a 400 at the edge. Prefixes are registered in one
table in `pkg/` and are never invented at a call site.

**Identifiers are not secrets.** A UUIDv7 discloses its creation time by
construction. Anything whose value depends on being unguessable — password
reset links, workspace invitations, public share links, API keys — uses a
separate 256-bit random token and never a UUIDv7.

## Consequences

### Positive

- Index entries are appended near the right edge of the B-tree, so inserts
  split few pages, write less WAL, and keep the hot part of the index in cache.
- The identifier exists before the transaction, so an aggregate, its outbox
  row, and any cross-service reference are all written in one round trip.
- No central sequence, so no coordination point between services.
- The prefix catches a whole class of identifier mix-ups at the API boundary,
  and makes logs and support tickets readable without a lookup.

### Negative / accepted costs

- 16 bytes rather than the 8 a `bigint` would cost, on top of the 16 bytes of
  `workspace_id` already in every key. Accepted: the alternative costs a
  database round trip before the row can be referenced at all.
- Creation time is public. This is a deliberate trade for index locality and
  is the reason for the rule about secrets above.
- Monotonicity holds within one process. A clock stepped backwards across a
  restart produces identifiers that sort out of order, which is harmless only
  because nothing is allowed to depend on that sort order.
- Identifiers are 39 characters in URLs and are not human-memorable.

### Neutral

- The wire format is reversible; the storage format is not. Changing how an
  identifier is rendered touches one serialisation layer, so this ADR is firm
  about `uuid` in the database and deliberately cheap to revisit above it.

## Alternatives considered

| Option                   | Why not                                                                                                                                                                                                    |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bigserial` / `identity` | The identifier does not exist until the database assigns it, so an outbox payload or a cross-service reference cannot be built before commit; also trivially enumerable                                    |
| UUIDv4                   | Random insertion order destroys B-tree locality: page splits on every insert, full-page WAL writes, and a buffer cache hit rate that degrades as the table grows                                           |
| ULID                     | Identical 48-bit millisecond layout and identical benefits, but it is not a native PostgreSQL type and carries no version or variant bits; UUIDv7 gets `uuid` storage, driver support and tooling for free |
| Snowflake / Sonyflake    | Requires node-id assignment and a clock-discipline story to buy nothing that UUIDv7 does not already provide at this scale                                                                                 |
| Composite natural keys   | Business data changes, and a key that changes is not a key                                                                                                                                                 |

## Revisit when

- URL length or identifier legibility becomes a real complaint rather than an
  aesthetic one. The fix is Crockford base32 at the serialisation boundary
  alone — 26 characters, storage untouched.
- A single table passes roughly 100 million rows, where 8 bytes per index entry
  becomes measurable against available RAM.
- Writes ever span more than one node, at which point the clock-skew assumption
  behind millisecond ordering needs restating rather than assuming.
