# Proposed tasks: Identity password login and sessions

Module id: `identity-password-login-and-sessions`

Review this list with [the plan](identity-password-login-and-sessions.md) before creating issues. Each task becomes one issue in the repository GitHub Project. Apply the accepted [session security profile](../docs/adr/0035-identity-uses-a-bounded-session-security-profile.md) and the signup module's [email outbox decision](../docs/adr/0036-identity-delivers-email-through-a-redpanda-outbox.md).

## Task 1: Extend the Identity contract for password sessions

Description: Add the five RPCs and four public REST routes to the existing `flowspace.identity.v1` contract. Keep the internal session check without an HTTP annotation.

Acceptance criteria:

- [ ] Login, refresh, current logout, all-session logout, and `CheckSession` expose the request and response fields in the approved spec.
- [ ] Login and refresh have no bearer requirement. Logout uses the caller's token and exposes no target subject or session field.
- [ ] Generated code matches the Protobuf source, and compatibility with `main` succeeds.

Verification: Run `task buf -- lint`, `task buf -- generate`, `task buf -- breaking --against '.git#branch=main'`, and the applicable contract tests.

Dependencies: The signup contract. Inspect merged signup code and issues first so this task extends its contract once.

Likely files: `contracts/proto/flowspace/identity/v1/`, `gen/go/flowspace/identity/v1/`, `contracts/http/` if generation already owns that output.

## Task 2: Sign in with a password through the public API

Description: Add one complete password-login path that reuses signup's account lookup, Argon2id verifier, session issuer, database, and Identity server.

Acceptance criteria:

- [ ] A correct password creates one session and returns the stable subject, current email state, distinct access and refresh tokens, and all required expiry times.
- [ ] Missing, retired, and wrong-password accounts return the same safe error and practical timing, with no session. An unverified account can log in.
- [ ] Request shape and the PostgreSQL-backed 30-per-IP-in-ten-minutes and ten-per-email-in-15-minutes limits run before password hashing. Limit-store failure returns `Unavailable`.

Verification: Run `go test ./services/identity/...`, `go test -tags=integration ./services/identity/...`, and public REST and RPC tests for errors, timing, limits, and lost-response login recovery.

Dependencies: Task 1, plus merged signup account, password, and session foundations.

Likely files: `services/identity/internal/app/`, `services/identity/internal/adapter/in/http/`, `services/identity/internal/adapter/out/postgres/`, `services/identity/db/queries/`, and tests beside changed code.

## Task 3: Publish and rotate public signing keys

Description: Expose Identity public keys at `/.well-known/jwks.json`, store an encrypted keyring outside PostgreSQL, and rotate it automatically every 24 hours.

Acceptance criteria:

- [ ] JWKS publishes only approved public keys, while the private key remains confined to Identity.
- [ ] A new public key appears at least two minutes before Identity signs with it. The old public key remains for at least 11 minutes after its last signature.
- [ ] A restart resumes rotation from persisted state; emergency rotation revokes sessions and waits for cached keys to expire before issuing new tokens.
- [ ] Verifiers reject unknown key IDs, wrong algorithms, wrong issuers, and token-controlled key locations.

Verification: Run `go test ./services/identity/...` and focused key-rotation and JWKS transport tests. Inspect the published document for private fields.

Dependencies: Task 1, plus the signup token issuer.

Likely files: `services/identity/internal/adapter/in/http/`, `services/identity/internal/adapter/out/`, `services/identity/internal/bootstrap/`, and related tests.

## Task 4: Refresh a session with single-use tokens

Description: Add the public refresh path with atomic token rotation and durable replay detection for the same device session.

Acceptance criteria:

- [ ] A valid refresh consumes the old token once, stores only the new token hash, keeps the same session, advances idle expiry, and preserves absolute expiry.
- [ ] A known rotated token revokes its session and current token. An unknown or expired token returns the same safe error without identifying an account.
- [ ] Two concurrent refreshes cannot both succeed. A lost response followed by reuse revokes that session.

Verification: Run `go test ./services/identity/...` and `go test -tags=integration ./services/identity/...` with a controlled clock, concurrent refreshes, rollback, replay, and 30-day and 90-day boundaries.

Dependencies: Tasks 1 and 2, plus the shared session schema from signup.

Likely files: `services/identity/internal/app/`, `services/identity/internal/adapter/in/http/`, `services/identity/internal/adapter/out/postgres/`, `services/identity/db/queries/`, and related tests.

## Task 5: Log out the current session

Description: Revoke the session named by the caller's validated access token after Identity confirms that it is active.

Acceptance criteria:

- [ ] The route accepts one bearer access token and no client-selected subject or session ID.
- [ ] Revocation and refresh-token invalidation commit before success. Other device sessions remain active.
- [ ] A session check that starts after the commit rejects the old session. An already admitted request can finish.

Verification: Run `go test ./services/identity/...` and `go test -tags=integration ./services/identity/...` with transport authentication and a commit-boundary concurrency test.

Dependencies: Tasks 1 and 2.

Likely files: `services/identity/internal/app/`, `services/identity/internal/adapter/in/http/`, `services/identity/internal/adapter/out/postgres/`, and related tests.

## Task 6: Log out every session for an account

Description: Revoke all existing sessions for the caller's subject and serialize revocation with creation of another session for that subject.

Acceptance criteria:

- [ ] All existing sessions and refresh tokens stop working after the revocation commit.
- [ ] A login that commits after all-session logout creates an active session. A login committed before it is revoked.
- [ ] A caller cannot select another account, and a lost logout response never grants access to a revoked session.

Verification: Run `go test ./services/identity/...` and `go test -tags=integration ./services/identity/...` with two devices and concurrent login and logout.

Dependencies: Tasks 2 and 5.

Likely files: `services/identity/internal/app/`, `services/identity/internal/adapter/in/http/`, `services/identity/internal/adapter/out/postgres/`, and related tests.

## Task 7: Expose an authenticated internal session check

Description: Let authenticated protected services test the token subject and session ID against current Identity account and session records.

Acceptance criteria:

- [ ] `CheckSession` has no public REST route and requires a per-service internal bearer credential over TLS. It rejects an unauthenticated caller or a subject and session mismatch.
- [ ] Active checks return current `email_verified`. Retired, revoked, idle-expired, and absolute-expired sessions return `Unauthenticated`.
- [ ] Store failure and timeout return a temporary failure and never an active result. A check begun after logout commits sees revocation.

Verification: Run `go test ./services/identity/...` and `go test -tags=integration ./services/identity/...` for caller authentication, current email state, expiry boundaries, outage, and the logout race.

Dependencies: Tasks 1, 2, 5, and 6.

Likely files: `services/identity/internal/app/`, `services/identity/internal/adapter/in/http/`, `services/identity/internal/adapter/out/postgres/`, and related tests.

## Task 8: Admit Workspace requests through FlowSpace sessions

Description: Replace Workspace's Keycloak verifier with local FlowSpace access-token checks followed by a live `CheckSession` call on every protected request.

Acceptance criteria:

- [ ] Workspace rejects an invalid JWT before the internal call, retrieves JWKS from the configured internal HTTPS URL, and denies a revoked, expired, or unverified session before checking membership.
- [ ] Workspace makes a new authenticated session check for each request and denies admission on timeout, Identity outage, or malformed reply.
- [ ] Workspace still reads its own membership and role data. It does not trust token claims for workspace authorization.

Verification: Run `go test ./services/workspace/...`, `go test -tags=integration ./services/workspace/...`, and focused cross-service tests for unverified email, logout, expiry, and Identity outage.

Dependencies: Tasks 3 and 7.

Likely files: `services/workspace/internal/adapter/out/`, `services/workspace/internal/bootstrap/`, `services/workspace/internal/adapter/in/http/`, and related tests.

## Task 9: Prove public and cross-service failure paths

Description: Record final evidence for every success criterion and threat mapping in the approved spec, then run the repository review gates.

Acceptance criteria:

- [ ] Every applicable requirement in the spec and ID-T01, ID-T02, and ID-T09 through ID-T17 has test or review evidence. Report unresolved failures before review.

Record exact results in the PR.

Dependencies: Tasks 2 through 8.

Likely files: `services/identity/`, `services/workspace/`, `tests/smoke/`, `tests/load/`, and the task PR.
